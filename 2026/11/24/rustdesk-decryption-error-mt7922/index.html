RustDesk 反复弹出 decryption error？元凶是 MediaTek MT7922 无线网卡驱动

用自建中继的 RustDesk 远程控制一台用 Wi-Fi 上网的 Windows 笔记本，主控端时不时报 decryption error 然后断开。有时几分钟内反复重连都失败，有时又能正常用几个小时。

排查下来，RustDesk、中继服务器、主控端都没有问题。真正的元凶是被控端笔记本的 MediaTek MT7922 无线网卡驱动：它会把本机发出的 TCP 数据改坏。RustDesk 的端到端加密检测到了被改动的数据，于是断开会话。

这个问题只在特定的无线环境下触发。笔记本换到另一个 Wi-Fi 之后，测试全部干净，RustDesk 也不再报错。但出问题的代码仍在笔记本的驱动里，换到类似的环境下可能再次出现。

下面记录现象、排查过程、测试数据和解决办法。

现象

  • 两端都是 RustDesk 1.5.1，服务器是开源版 hbbs + hbbr 1.1.16，会话走中继。
  • 被控端是一台用 Wi-Fi 上网的 Windows 11 笔记本（机械革命蛟龙系列），网卡是 MediaTek Wi-Fi 6E MT7922 160MHz，驱动是 mtkwl6ex.sys。
  • 出问题时主控端弹出 decryption error，会话断开，大约每 2 秒自动重连一次，每次连上一两秒到几秒又断。
  • 时好时坏：有时连续几分钟连不上，有时能稳定用几个小时。
  • 笔记本换到另一个 Wi-Fi（2.4 GHz，802.11ax）后不再出现。

decryption error 是什么意思

RustDesk 两端之间的数据是逐帧加密的。它的实现在 hbb_common/src/tcp.rs（AGPL-3.0），用一个按方向各自递增的计数器当 nonce，下面是原文节选：

接收端按顺序用第 1、2、3……号 nonce 去解每一帧。某一帧解不开，就返回 decryption error，会话结束。

所以这个报错不是“密码错”或“Key 配错”，那种情况根本连不上。它的准确含义是：握手和登录都成功了，会话中途有一帧数据校验失败。原因只有两类：某一帧丢了导致序号错位，或者某一帧的内容被改了。

排查过程

1. 排除服务器和配置

看中继日志和被控端日志：每一次连接都配对成功、登录成功，然后过 1~8 秒断开。两端版本一致，服务器密钥没变过。服务器和配置都没有问题。

2. 抓包看到了“矛盾”

我让中继服务器在日志里出现连续断开时自动抓包。抓到的失败会话有三个共同点：

  • 每次都是主控端先关闭连接。
  • 被控端写进 socket 的字节，和主控端收到的字节逐字节相同，一次会话里比对了约 200 万字节。
  • 字节流是完整、连续的帧序列，没有缺帧或错位。

这说明从被控端的 socket 到主控端的 socket 之间，数据是完好的。问题出在抓包点看不见的地方：被控端的 TCP 协议栈内部，或者主控端收到之后。

3. 不看抓包，直接比对数据

既然抓包看不到，就绕开它：从被控端发一段可复现的伪随机数据到服务器，由接收端逐块重新生成并比对。第一次 16 MB 完全一致，第二次 64 MB 两端 SHA256 不同，但字节数相同。问题复现了：数据被改了，但没有多也没有少。

4. 看清被改成了什么

换成可复现的确定性数据流之后，能逐字节找出被改的位置和内容。被改的总是成小段的几个到几十个字节，换进来的内容是固定的几种：

这些是 802.11 管理帧（例如信标帧）里的信息元素。也就是说，无线网卡收到的帧内容，被写进了本机正在发送的 TCP 数据里。

5. 对照实验

  • 同一台机器上，发送端和接收端都走 127.0.0.1，传 256 MB：0 块被改。内存和 CPU 没有问题。
  • 反方向（服务器发到这台机器）16 MB：0 块被改。只有发送方向有问题。
  • 在服务器上用 tcpdump 看被改动的包：1427 个数据包的 TCP 校验和全部是 correct。说明改坏发生在被控端计算校验和之前，不是路上坏的。

结论：问题在被控端无线网卡的发送路径上。

6. 换到另一个 Wi-Fi 之后

把笔记本换到另一台路由器的 Wi-Fi 上（2.4 GHz，802.11ax），出口运营商没有变，再用同样的方法测：

测试 被改动的块
64 MB 全速 × 3 轮（约 13 Mbps） 每轮 1024 块中 0、0、0
32 MB 限速 2 Mbps 512 块中 0

而原来那个 Wi-Fi（5 GHz，802.11ac）下，每一轮测试都有改动。所以这个问题确实和所连的 Wi-Fi 有关，换一个 Wi-Fi 也是目前最省事的规避办法。

那是不是原来那个网络的问题？我认为不是，改动发生在笔记本内部，理由有三条：

  • 换进来的内容是 802.11 管理帧里的信息元素。这类数据只存在于无线网卡和驱动里，路由器另一侧的网络设备既收不到无线帧，也不可能把它写进 TCP 数据。
  • 改动的位置和笔记本上应用每次 send() 的数据块对齐，规律见下一节的“奇偶”那条。网络上的设备看到的只是一段段独立的 TCP 报文，不知道哪几段来自同一次发送。
  • 被改的包 TCP 校验和是正确的，而回环和反方向都干净。

更合理的解释是：驱动里的缺陷一直在，但只在原来那个 AP 的无线模式下才会触发，比如 5 GHz、802.11ac 这些特性对应的发送路径。

我没有做的一个对照是用网线接原来那台路由器再测一次。如果那条也是干净的，就能直接说明路由器外侧的网络没有问题。

测出来的规律

测试方法同上：每块 64 KiB，接收端逐块比对，统计被改动的块数。前五行都在出问题的那个 Wi-Fi 上测，第六、七行是换到另一个 Wi-Fi 之后，最后两行是对照。

驱动版本 发送速率 数据量 被改动的块
3.4.0.1123 全速（约 30~40 Mbps） 64 MB × 3 轮 每轮 1024 块中 124、131、141
3.5.2.1383 全速（约 30~40 Mbps） 64 MB × 3 轮 131、141、161
3.5.2.1383 全速（约 70 Mbps） 64 MB × 3 轮 0、8、12
3.5.2.1383 2 Mbps 32 MB × 3 轮 每轮 512 块中 14、18、18
3.5.2.1383 0.5 Mbps 8 MB 128 块中 1
3.5.2.1383 全速（约 13 Mbps），换到另一个 Wi-Fi 64 MB × 3 轮 0、0、0
3.5.2.1383 2 Mbps，换到另一个 Wi-Fi 32 MB 512 块中 0
对照 127.0.0.1 回环 256 MB 0
对照 反方向（对端发到本机） 16 MB 0
  • 发得越快，越容易被改。 全速时大约每 0.5 MB 就有一处，2 Mbps 时大约每 2 MB 一处，0.5 Mbps 时 8 MB 才一处。这解释了为什么远程桌面在画面静止时很稳定，画面一开始变化就频繁断开。
  • 问题时轻时重。 同一台机器同一个脚本，下午的比例比晚上高一个数量级，也有个别一轮完全干净。
  • 更新驱动没有解决。 从 3.4.0.1123 升到 3.5.2.1383 之后，测试结果没有变化。
  • 限速发送时，被改的是大块发送末尾的几个字节。 限速到每次只有一个 send() 在途时，改动全部从数据块内部偏移 742 + 1424 × k 的位置开始（1424 是抓包看到的 TCP 每段数据长度），也就是这次发送末尾 127 字节的起点。其中一轮里，末尾恰好只剩 127 字节的大块发送共 37 次，18 次被改；末尾剩 28 字节以上的都没有被改。同一组数据发两次，两次各 18 处改动，其中 16 处位置相同。
  • 奇偶规律。 还是那一轮，把末尾只剩 127 字节的大块发送按“末尾前面有几个 1424 字节的边界”分类：边界数是奇数的 14 次一次都没有被改，是偶数的 23 次里有 18 次被改。另外 3423 次 6003500 字节的中小块发送里没有任何改动。这种只和本机单次 send() 内部布局有关的规律，说明改动发生在笔记本自己这一侧。
  • 全速发送时位置不固定，并且成簇出现。 64 MB 里的十几处改动集中在不到一秒内。

我的猜测是驱动在发送路径上处理大块数据的分段时，比如大量发送卸载，最后不足一段的数据没有被正确填入，发出去的是缓冲区里残留的内容。这只是根据现象的推测，具体原因要驱动厂商才能确认。

影响范围

这个问题影响这台机器通过 Wi-Fi 发出的所有数据：

  • 自带完整性校验的协议会报错或断开，例如 RustDesk 的 decryption error、SSH 连接莫名中断。
  • 没有校验的上传会被悄悄改坏，例如文件上传、git push、网盘同步。

如果你的机器用 Wi-Fi 时遇到“上传的文件哈希不对”“SSH 老是断”“远程桌面报解密错误”，而换个网络就好了，可以用下面的脚本自查。

怎么解决

  1. 换一个 Wi-Fi 或换一个频段。 换到另一台路由器后，4 轮测试全部干净，RustDesk 也不再报错。这是目前最省事的办法，但驱动里的问题还在。
  2. 插网线。 最可靠，直接绕开出问题的驱动。
  3. 更新或回退无线网卡驱动。 我这里从 3.4.0.1123 更新到 3.5.2.1383 没有效果，但别的版本或别的机型未必。
  4. 换一块网卡。 比如换一个其他芯片的 USB 无线网卡。
  5. 临时办法：让流量走带完整性校验的隧道，例如 WireGuard、Tailscale。隧道会把被改坏的包识别出来并丢弃，由里面的 TCP 重传。这一条我没有实测，是根据隧道的工作原理推的。

走过的弯路

  • 一开始以为是 NAT 打洞的问题，把 TCP 打洞关了。和这个问题无关。
  • 中途看 TTL 和 SYN 指纹，怀疑链路上有透明代理。也是错的。
  • 最耽误时间的一个误区：看到抓包里两端字节完全一致，就认为“数据损坏”已经被排除。实际上抓包点在服务器上，被控端在计算校验和之前发生的改动，到了网络上已经是“校验正确”的数据了。

回头看，真正有效的两步是：不依赖抓包，直接在应用层做端到端比对；以及用可复现的确定性数据去测。这样不仅能知道“坏了”，还能看清坏在哪里、坏成了什么。
